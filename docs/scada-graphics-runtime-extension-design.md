# 画像・描画表現・Faceplate・画面展開・kioskの拡張検討

初版2026-10-19、用語確認反映2026-10-20（日本時間）。ユーザーからの追加要望を[統合設計](scada-integrated-design.md)へ取り込むための**検討案**。Astraが現行コード・上流設計と照合した。追加機能を実装済み、提供版を確定済みとする文書ではない。現在の実装はProject 0.14.0・ローカルDesignerで、正式Runtime／Host・画像資産・Equipment／Actionは未実装。

Banto基盤を維持し、認証はindustrial側の修正後まで延期する。リリース前のProject互換性を維持するためにモデル変更を避けず、変更時はRust／TypeScript／schema／生成経路・サンプル・検証を揃える。ems-appsの画面・コード・画像は取り込まない。

## 1. 全体評価と確定した用語

2026-10-20のユーザー回答により、次の意味で設計へ取り込む。機能の意味を確定したもので、実装完了や詳細仕様・提供版の確定を示すものではない。

| 用語               | ユーザーが指定した意味                   | 今回の対象                                                    |

## 実装状況の追記（2026-10-20）

[実線・破線・点線](line-style-design.md)をProject 0.13.0で実装した。単独／一括編集と共通描画へ接続し、矢印・連続したhit領域を保持する。続けて[配置全体の不透明度](opacity-design.md)をProject 0.14.0で実装した。paint再編・色ごとのα・gradient／pattern・画像・画面展開は引き続き後続で、描画基盤全体の完成とはしない。

## 2. Paint・線種・αを先行する

現行の `fill: #RRGGBB`、ShapePaint、Polylineの線幅をそのまま文字列だけで拡張せず、色とpaintの責務を整理する。

- 色はRGBとαを明示して扱う。UIは「不透明度 0〜100%」、保存は有限な0〜1の値を候補とする。
- 塗りは `none / solid / linearGradient / radialGradient / pattern` 等の判別型。線は色・幅・線種・capを持つ。最初から全種類を実装済み扱いにしない。
- 配置全体のopacityはpaintのαと独立する。Symbolなどは内部の描画を合成したグループへ1回だけ適用し、選択枠・ハンドルを薄くしない。
- 「塗りなし」「色α=0」「配置opacity=0」「visible=false」は別の状態。透明な図形も編集用hit領域やレイヤーから選べるようにする。
- Editorの暗い／明るい外枠を切り替えても、保存色・α・背景画像を変更しない。透明確認用の市松はInspector内の見本に使い、工程図の背景へ勝手に追加しない。

線形gradientの角度・stop、放射gradientの中心・半径は配置のlocal座標基準にする。回転・リサイズと一緒に変換し、画面上の倍率に依存しない。最初は2色を数値指定し、多点stopやキャンバス上の制御ハンドルを後続へ分ける。ハッチは原点・間隔・回転の単位を保存し、ズーム時に模様がずれないようにする。

線種は共通プリセットから始める。間隔を線幅の倍率として定義し、点線のround capが潰れない間隔を確認する。矢印の先端は実線の形を保ち、最後の頂点と同じ向きを使う。破線の隙間で配置が選べなくならないよう、編集のhit領域は既存の連続した線を維持する。

### 共有Symbolと一括編集

定義色モードはpaintを保持する。単色モードでは配置色で各paintのRGBを置換し、stop・patternのα、線幅、形状を保持する案を推奨する。たとえば不透明な2色gradientは同じ色になるが、αの変化は残す。変更の意味を表示し、異なるpaintを含む複数選択を黙って単色へ変換しない。

単色Symbolの配置色にもαを持たせる場合は、内部paintのαとは分ける。配置色αと配置opacityの積を、合成後のSymbolグループへ一度だけ適用し、各子要素へ重複適用しない。定義色モードでは保存された配置色とそのαを描画へ使わず、配置opacityと内部paintのαを使う。この規則をpaint詳細仕様と重なりの検証へ引き継ぐ。

画像の単色化は別仕様になるため、Imageの初期範囲は画面直置きと背景に限定する。Symbol内部へのImage追加は、色モードと資産依存の規則を決めてから広げる。

## 3. 背景画像・Image・clipboard

### 共通資産を先に用意する

ProjectはassetのID／content hash・メタデータを参照し、バイト列は不変のAssetStoreへ保持する。現在のEditorはProjectを複製して履歴を作るため、配置ごと・Undoごとにbase64を埋め込むと容量と編集時間が増える。画像を単にSVG imageへ渡すだけでは保存機能の完成にならない。

上流の[Project package設計 §5](upstream/industrial/scada-design.md#5-project-import--export)に合わせ、`assets/`を含めて持ち運べる保存・読込adapterを先行する。directory／ZIPは同じ論理モデルを使い、現在のJSON入出力との関係を決める。最小の資産保存を作っても、Design Domain・復旧・配布・正式package全体の完了とは呼ばない。

必要な契約は、参照解決・同一画像の共有・変更しないoriginal bytes・書出しへの同梱・欠損時の案内。削除後もUndoが参照するassetは保持し、単なる「画面上で未使用」だけで削除しない。ブラウザのblob URLや端末上の絶対パスを永続参照として保存しない。実サイズ・decode・合計容量の上限は実測で決める。

### 背景画像

背景色の上、全配置の下へ表示する。既定はcontain・中央配置。coverの切抜き、stretch、元サイズを別の選択肢として明示する。画像変更で画面寸法を自動変更しない。位置・表示方法・不透明度を画面設定から編集し、差替え・解除・Undoに対応する。

背景画像は通常の選択・範囲選択・全選択へ含めず、背景編集へ明示的に入る。解除では元の背景色を維持する。

### Image配置と貼付

初期はPNG／JPEGのファイル選択から始め、PNGの透明部分を保持する。画像decodeの成功後に登録と配置を1操作として確定する。縦横比維持を既定にし、幅・高さ・元比率へ戻す操作、回転、順序、lock／hidden、複製、Undo／JSONまたはpackage往復を既存操作へ接続する。トリミング、SVG、アニメーション、外部URL、色抜きは別工程にする。

画像貼付は次の工程。テキスト入力中の通常の貼付を奪わず、キャンバスの図形断片とOS画像を明確に識別する。現在の図形clipboardはtext/plainの4MiB制限であり、画像の受渡しへそのまま転用しない。別Projectへのコピーに必要なassetも扱い、端末内の一時IDだけをコピーしない。

非同期decode／clipboard待ちでは、開始時の世代・所有先・配置点を固定し、完了時に再検証する。取消・Project差替え・所有先切替後に遅れた画像を配置しない。画像の特定色を透明にするクロマキーは、通常のαと別の画素処理として原画像と設定を保持する後続機能。

## 4. 画面取込：別画面の埋込View

ユーザー指定は、別の画面を現在の画面の枠内へ表示する機能。初期は同一Project内の `screenId` を参照する専用配置を提案する。元画面を複製せず、参照先の変更を全使用先へ反映する。現行Symbolを別名にするのではなく、画面としての背景・寸法・配置・タグ参照を扱う。

### 表示と編集の境界

- 埋込枠は位置・幅・高さ・回転・表示／ロックを持ち、通常の選択・移動・サイズ変更・Undoへ接続する。枠の選択と内部の図形編集を混ぜず、「参照元画面を開く」で元画面を編集する。
- 既定は縦横比維持のcontain・中央配置とし、参照画面の背景も枠内へ描画する。枠外はclipし、内部のリサイズで参照元の寸法を変更しない。背景を透過する選択肢は別設定として明示する。
- 同じ画面を複数箇所へ埋め込んでも、参照元の図形・assetを配置ごとに複製しない。タグ購読は同じ参照を共有し、表示窓ごとに別のHub接続を作らない。
- 初期は1段の読み取り表示から始め、内部の操作・画面遷移・Popup呼出は後続として提案する。表示だけのプレビューを正式Runtimeや設備操作の実装済み扱いにしない。

### 参照の検証と使用先

自分自身・間接循環・参照切れを保存前と読込時の両方で拒否する。初期の1段制限を採る場合は、参照先がさらに埋込Viewを持つ構成も検証対象にする。将来の多段化では再帰の上限と描画・タグ要求の予算を設け、無制限に展開しない。

使用先一覧でどの画面から参照されているかを示し、使用中画面の削除を保護する。画面の複製・Project内clipboard・将来のコピーImportでは、元画面を共有するか新しい参照先へ対応付けるかを明示する。親画面の設備選択やcontextを、別設備の埋込表示へ暗黙に流さない。型付きEquipment contextはslot導入時の契約へ接続する。

### 今回の要望に含めない別機能

他Projectからの画面コピー取込、同一IDを保つ更新Import、スクリーンショット、他製品形式の変換は、それぞれ別の操作として残す。画像取込・背景設定は引き続き独立した要望として扱う。画面の埋込表示を実装しても、他製品の図形・タグ・動作の変換ができるとは説明しない。

## 5. Faceplate・popup・kiosk

### Faceplate

上流[§7](upstream/industrial/scada-design.md#7-equipment--symbol--faceplate--dialog)のEquipmentType／EquipmentInstance・型付きslotを先に定義する。SymbolとFaceplateは同じ設備contextを使い、タグをそれぞれへ二重設定しない。最初は設備名・数値・品質を表示する読み取り専用の詳細Viewから始める。

設備contextが変わったら旧設備の値を持ち越さず、世代・参照先を再確認する。未取得／Bad／Staleは既存の品質表示へ揃える。静的な詳細図のプレビューと、実Hubへ接続したFaceplateの提供段階を分ける。

運転操作・書込みは基本Action・Host・Hubの書込み経路と上流認証の契約が揃ってから接続する。今回の検討を理由にSCADA独自の認証を作らない。Alarm／TrendをFaceplateへ配置する設計は維持するが、エンジンの提供はS9b上のv1.1という既存計画を変更しない。

### 子ウィンドウ：監視画面内PopupとView Stack

ユーザー指定は監視画面内に開く小窓。通常の設備詳細は非モーダルPopup、確認・数値入力はModalとして分ける。Equipment専用のFaceplateと、設備に限定しない汎用Dialog／Popupも区別する。

非モーダル小窓は対象設備名・見出し、移動・前面化・閉じる・フォーカス復帰・画面外へのはみ出しを管理する。背面の監視を継続でき、Modalのfocus trapや背景操作禁止をそのまま流用しない。確認には固定依存Banto v6.7.0のModalとclose guardを利用する。

同じ定義・同じ設備contextを再度開いた場合は既存の小窓を前面へ出す案を既定とし、別設備の小窓は混同しない。初期は読み取り表示を優先する。画面切替・参照元の削除・Project差替え時の存続／終了と遅れた値の破棄を定義し、閉じた小窓が値更新で再出現しないようにする。

OS／ブラウザの独立した別窓は今回の対象外。将来追加する場合は、Host・window／webviewの権限、親子の終了、同じProject revisionと設備context、購読・切断状態の共有が必要。ブラウザでは利用者操作に起因しない別窓が制限される。小窓を閉じても設備操作や警報ACKを意味しない。

上流のView Stack（Process Screen→Faceplate／Popup→Modal→System Overlay）を維持する。将来の重要な状態表示を小窓の背後へ隠さない。Designerのサイドパネルの浮動／ドッキングとは別の工程にし、相互の必須前提にしない。

### kiosk

開発用には「全画面で表示確認」を小さく先行できる。Fullscreen APIまたはブラウザの全画面表示を使い、Escで戻る。編集データと表示中心を保ち、正式Runtimeや操作権限の切替とは呼ばない。

本番kioskはHostと運用設定で実装する。起動時Runtime mode／capability、配布済みProject・起動画面、再起動後の閲覧専用復帰、画面比率・DPI・対象モニター、通信断・復旧、管理者の終了経路を含める。ブラウザFullscreenだけでOSの切替や離脱を防ぐことはできず、必要なら端末のOS kiosk設定も組み合わせる。

再起動時にログインなしで監視へ入る要望は[アクセス方針](access-policy.md)を維持する。管理者として自動ログインせず、設定変更・設備操作の認証は上流統合後に実装する。認証サービス障害で編集可能な開発モードへ自動的に戻さない。今回のPopupは同じ監視画面内へ開き、kioskの全画面領域から外へ出さない。表示領域変更時は小窓を枠内へ収め、将来のOS別窓とは分ける。

## 6. 実装順の提案と受入

ユーザー回答を反映し、次の順を提案する。これは追加要望の実装完了・全機能の着手宣言ではない。

1. **描画基盤**：paintの整理、線種、色α・配置opacity。単色／定義色Symbolと複数選択の明示操作を揃える。
2. **画像の保存基盤**：AssetStoreと持ち運べる入出力。画像の共有・Undo保持・欠損・容量を検証した後、背景画像／Image配置へ接続する。
3. **表現と貼付**：線形／放射gradient、画像clipboard。メッシュとして斜線・網掛け・点のpatternを追加する。
4. **画面と表示の再利用**：同一Project内の埋込Viewと、監視画面内Popupを段階的に追加する。参照・viewport・使用先を共通化し、初期の読取表示はEquipment／実Hub接続と切り離して検証できるようにする。
5. **設備・運用**：Equipment／slot→読み取りFaceplate→正式Runtime／Hostと本番kiosk。全画面での開発用表示確認は独立して先行可能。

各段階でRust／TypeScriptの保存契約、Undo／Redo・複製・clipboard・取込、Editor／表示プレビュー／ミニマップ／共有定義、両テーマ・回転・透明背景を検証する。非同期取消とProject差替え、参照欠損、元の値と見た目の違いを受入条件へ含める。自由メッシュグラデーション・他製品converter・OS別窓は今回の対象外とし、将来別に要望された場合の調査項目として残す。

## 7. Banto／industrialとの境界

Bantoのテーマ・Menu・Modal／Drawer・入力保護を継続利用する。SCADAのpaint・資産・Equipment・View StackはSCADA側の責務とする。正式Runtime・本番kioskのcapabilityはHostとの契約で扱い、Editor UIを隠すだけで運用モードを作らない。

現時点で上流Issueの作成が必要な確定障害はない。Hostや認証の公開契約で不足が判明した段階で、再現条件・必要API・責務境界を明記したIssueをBantoまたはindustrialへ作成する。上流の参照スナップショットは編集しない。

## レビュー記録

Astraが本案の現行コード・上流設計との整合を確認した。AssetStoreとUndoの責務、用語を未確定のまま比較する方針、Faceplate／Host／認証／kioskの段階に重大な矛盾はなかった。単色Symbolの配置色αを合成後のグループへ一度適用する指摘を上記へ反映した。2026-10-20のユーザー回答により、埋込View・繰返しパターン・監視画面内Popupへ範囲を具体化した。詳細実装と受入試験はこれから行う。
