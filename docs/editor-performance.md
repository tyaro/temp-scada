# 編集性能の計測（R6）

R0〜R5の構造整理後、最適化の対象を実測で選ぶための記録。ブラウザの描画・入力遅延や対応可能な設備規模の保証ではない。

## 再現方法

```sh
source scripts/cloud-env.sh
pnpm --filter banto-scada benchmark:editor
# 配置数を指定する場合（10〜10,000）
pnpm --filter banto-scada benchmark:editor 1000
```

計測結果のJSONをstdout、進行をstderrへ出す。JSONを保存する場合はpnpmのログを避け、リポジトリルートで`node --expose-gc apps/banto-scada/scripts/benchmark-editor.mjs > /tmp/editor-benchmark.json`を使う。ViteのSSR loaderで実際のTSモジュールを読み込み、サーバーをlistenせずに実行する。新しい依存や性能テスト用の本番コード分岐はない。

fixtureは現行minimalサンプルの矩形・楕円・テキストをほぼ同数配置する。UUID・orderは重複させず、1画面1,000配置という保存契約に従い、5,000配置は5画面に分ける。最初の図形を編集するが、検証・コピー・履歴はProject全体が対象。画像資産・共有Symbol・フォルダー・埋込画面・タグは含めない。

各操作は1回warmup後に9回計測し、中央値と最大値を出す。GCは各計測の前に実行し、計測区間から除く。最大値はこの9回の最大であり、p95や最悪時間ではない。連続移動は同じ図形を1ずつ動かして50回確定し、各回のドメイン処理を測る。ドラッグ中の毎フレーム処理や描画時間ではない。

開始・終了時にGCし、50件の履歴と最新Projectを保持したheapUsed／RSSの差を出す。スナップショットのUTF-8合計サイズも別に記録する。V8の文字列表現・GC・アロケータの影響があるため、差は正確な履歴専用メモリ量でもピーク使用量でもない。計測スクリプトは元Project不変、Undoの内容復元、履歴件数、移動結果をassertする。

## 候補コピーの限定改善（R6b）

候補生成を`parseProject(serializeProject(project))`から`parseProject(JSON.stringify(project))`へ変更した。前者のserializeは整形JSONをparserで検証した後、parserの正規化結果を捨てて文字列を返し、直後に同じ内容をもう一度parseしていた。変更後もhandlerより先に同じparserを通し、schema・ID・参照・legacy正規化の検証と独立した候補を維持する。finish・履歴・保存用serializeは変更しない。

同じ環境・fixture・回数で測った[変更後の生JSON](performance/r6-after-copy.json)。基準アプリ`4daf011`＋候補コピー変更。表は中央値、ms。これは各1回の計測runの比較であり、統計的な性能保証ではない。

| 操作               | 100配置（前→後） | 1,000配置（前→後） | 5,000配置（前→後） |
| ------------------ | ---------------: | -----------------: | -----------------: |
| 編集               |      5.509→6.177 |      48.024→39.626 |    250.508→197.084 |
| 履歴付き編集       |      7.404→6.210 |      59.014→53.813 |    311.348→249.991 |
| 50回の連続移動確定 |      5.737→4.876 |      59.874→50.773 |    330.566→262.125 |
| Undo（処理未変更） |      3.787→4.913 |      35.032→32.573 |    173.322→173.843 |
| 保存（処理未変更） |      1.438→1.336 |      11.221→10.685 |      50.640→51.874 |

変更後run内で旧コピーと新コピーを独立に測ると、5,000配置では95.754ms→43.435msだった。生JSONの`cloneWithValidation`は旧経路の比較probe、`candidateCloneWithValidation`が新しい候補経路。基準JSONには後者がない。アプリ全体の編集時間も大きなfixtureで減ったため、この限定変更を採用する。100配置の編集中央値は増えており、小規模での改善は主張しない。

不正な元Projectを図形削除で修復できそうな場合でも、handler前の検証で拒否する回帰ケースを追加した（未知property・非有限座標・重複ID・Symbol参照切れ）。元Project・履歴が変わらないことを含め、既存のno-op・正規化・Undo・保存契約のテストと合わせて確認する。Astraの静的レビューでも、同じparserによる検証・独立候補・正規化の保証を維持すると確認した。

ローカル検証は型（エラー／警告なし）・TS641件・関連ブラウザ30件・本番ビルド・全体整形が成功した。Rust／schema／現行サンプルは変更していない。最終差分の全体CIはPush後に確認する。

履歴を50件分保持する仕組みは変えていない。画像を含むメモリ対策や全ての編集を一定時間以内に収める最適化が完了したという意味ではない。

## 今後の判断

大きなProjectでは画面をまたぐ検証・コピー・比較・履歴生成の費用が見える。今回の限定改善で候補コピーの重複を減らし、それ以外は後続機能で実図面の問題が確認された時点で再評価する。

canonical比較と履歴保持も費用があるが、差分Undo・大域cache・検証省略はこの結果だけでは採用しない。資産なしfixtureで資産収集が軽かったことを、画像を含むProjectにも一般化しない。今後画像・Symbol・参照を含む実図面やブラウザ上の操作に問題が出た場合、同じ条件で再現・計測して別工程で扱う。
