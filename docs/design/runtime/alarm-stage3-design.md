# 段階3 警報の設計（製品hostの暫定Engine）

状態: **設計（2026-11-14 ユーザー承認・未実装）**。2026-11-14 作成。[フロー図の差分](../editor/flow-diagram-gap-2026-11-12.md)§3 の段階3「8. 警報」を、製品 host に暫定で置く形で具体化する。§9 の確認事項は 2026-11-14 にすべて回答を得た。

## 1. 目的と範囲

オーナー提供の参照画面にある次の要素を、運転表示で使えるようにする。

- 数値の横の HH／H／L／LL の小札（状態で色が変わり、未確認は点滅する）。
- 画面の枠の上端の「最新の警報」の帯と、「アラーム履歴」「ブザー停止」のボタン。
- 機器の故障などの bit を警報として、帯と履歴に出す。

範囲外: Shelve、latch、PLC 側の ACK・リセットの bit との連動、複数端末での ACK の共有、冗長化、24/365 の常駐、印刷、警報の Replay、機器種別の slot に持たせる警報の雛形（§8）。

## 2. 前提

上流（[上流 SCADA 設計](../../upstream/industrial/scada-design.md)。2026-11-14 時点の上流 main と差分なし）:

- §11.1: 警報は Alarm Source → Alarm Engine（AlarmDefinition／AlarmState／AlarmEvent／AlarmHistory）の汎用 domain。read-only の警報状態タグは projection としてなら公開してよく、正本にはしない。
- §11.2（2026-10-08 オーナー決定）: HH／H／L／LL のしきい値は使う側（SCADA）が持って判定する。Hub は持たず、判定もしない。判定に使ったしきい値はイベントに残す。
- §11.3: 状態の候補は Normal／Pending／ActiveUnacked／ActiveAcked／ReturnedUnacked／Shelved。定義の候補は source、severity、message、deadband、on delay、off delay、latch、enabled。設定 UI は単純な条件から始めてよい。
- §11.4: ACK／Shelve は Engine の操作者の状態で、PLC の ACK bit・リセットとは初版で結合しない。
- §11.6・§21 S10: Engine は独立 crate の候補（`banto-alarm`）で、host は SCADA server core（S9b の上の v1.1）。
- Hub はしきい値・警報 API・警報イベントを持たない。タグの属性は単位・小数桁・書込可否だけ。
- 上流 Issue tyaro/banto-industrial#725（警報の評価の場所）は open のまま。§11.2 の決定より前の整理で、この設計は §11.2 に従う。

この repo（[統合設計](../scada-integrated-design.md)§6、[開発計画](../../project/development-plan.md)）:

- 警報の評価・ACK・警報イベントは SCADA server の責務。Historian とは論理的に分ける。Historian の障害や履歴の照会で、警報の評価を止めない。
- 警報 ACK は設備操作と同じ列にある（[アクセス方針](access-policy.md)）。運用・未ログインでは不可。
- 点滅は既定で使わず、動きを減らす OS 設定へ追従する（[フロントエンド UX 設計](../editor/frontend-ux-design.md)）。色と文字の両方で状態を示す。

ユーザー決定（2026-11-14）:

- 評価は製品 host（Tauri の埋込 host。Historian の記録と同じプロセス）に暫定で置く。評価の本体は独立 crate にして、後で SCADA server core へ移せる形にする。
- 発生元はしきい値（数値タグの HH／H／L／LL）と bit（true／false で警報）の両方。
- PLC 側でしきい値を判定する案件では、PLC が最終的に bit を立てるので、その bit を bit の定義で警報にし、SCADA のしきい値の定義は作らない（PLC 側だけを使う）。どちらで判定するかは案件・信号ごとに利用者が決め、同じ警報を両方で定義しないよう Designer で重複を検出する仕組みは作らない。

## 3. モデル（Project）

Project 直下の任意の `alarms`。schemaVersion は据え置く（リリース前の Project は後方互換を保証しない）。

```jsonc
"alarms": {
  "blinkUnacked": false,              // 任意。§7
  "definitions": [
    {
      "id": "<UUID v7>",
      "name": "T-101 温度",             // 帯・履歴に出す名前（1〜100文字）
      "enabled": true,
      "source": {
        "kind": "threshold",
        "tag": "PLANT.T101.PV",          // タグの外部名
        "limits": {                       // 1つ以上。HH ≥ H > L ≥ LL を検査
          "hh": { "value": 95, "severity": "high", "message": "温度 異常高" },
          "h":  { "value": 85, "severity": "medium" },
          "l":  { "value": 5,  "severity": "medium" }
        },
        "deadband": 1.0                   // 任意。復帰は限界から deadband 戻ったとき
      },
      "onDelayMs": 0,                     // 任意。0〜600000
      "ackMode": "manual",                // 任意。§3 の ACK の種類
      "offDelayMs": 0
    },
    {
      "id": "<UUID v7>",
      "name": "P-201 一括故障",
      "enabled": true,
      "source": { "kind": "bit", "tag": "PLANT.P201.FAULT", "activeWhen": true },
      "severity": "high",
      "message": "ポンプ 一括故障"
    }
  ]
}
```

- 状態を持つ単位（condition）は、しきい値なら定義×限界（`<定義id>:hh` など）、bit なら定義そのもの。
- severity は `high`／`medium`／`low` の3段にする（色と並び順に使う）。数値の重要度は後で必要になったら足す。
- message は任意で、無ければ「名前＋限界の名前」を出す。
- ACK の種類 `ackMode`（定義ごと、任意。案件によって自動で ACK・復帰したい警報があるため。2026-11-14 ユーザー指示）:

  | 値               | 動き                                                                                                                            |
  | ---------------- | ------------------------------------------------------------------------------------------------------------------------------- |
  | `manual`（既定） | 発生で未確認になり、ブザーが鳴る。ACK するまで残る（復帰しても ReturnedUnacked）                                                |
  | `autoOnReturn`   | 発生で未確認になり、ブザーが鳴る。手で ACK もできる。復帰したら自動で確認済みにして Normal に戻す（ReturnedUnacked を作らない） |
  | `none`           | ACK 不要。発生のときから確認済み（ActiveAcked）で、ブザーは鳴らさない。帯・一覧・履歴には出て、復帰で消える                     |
  | `noneWithSound`  | `none` と同じだが、発生のときにブザーを一度だけ鳴らす（鳴り続けない）                                                           |

- 検査: タグの外部名の形式、限界の順序と値が有限であること、deadband が有限で 0 以上であること（上の限界（HH・H）と下の限界（L・LL）を両方持つ定義では、deadband が最も低い上の限界と最も高い下の限界の差より小さいこと。同じ値で高と低が同時に残ったり、発生と復帰を繰り返したりしないように）、bit の定義で bit 型以外のタグを、しきい値の定義で数値型（i16〜f64）以外のタグを指していないこと（型はタグ一覧があるときだけ）、名前と id の重複。実行時に型の合わない値（しきい値の定義で数値でない値、bit の定義で bool でない値）が届いたら、その condition を評価不能（理由は「型不一致」）にする。
- しきい値の限界は、それぞれ独立した condition として評価する。値が HH 以上になれば H も成立し、両方が発生する（上位の限界で下位を抑えない）。「成立」の定義は §4.2、表示の優先は §7。
- 編集: 「プロジェクト設定」に「警報の設定」を置き、一覧の表で編集する（追加・複製・削除・有効の切替）。Undo／Redo に乗せる。

## 4. 評価と状態

評価は新しい crate `crates/scada-alarm` に置く。上流 §11.6 の候補名は `banto-alarm` だが、industrial へ戻せる配置（`crates/scada-*`）を保つためにこの名前で作り、上流へ移すときに改める。入出力を持たない純粋な状態機械で、`step(状態, 入力) -> (次の状態, イベント)` の形にする。DB への書込みは host が行い、書けたときに次の状態を確定する（ACK・適用は書けなければ前の状態のまま。§5.3）。全入力×全状態の遷移表を 3-A の fixture（`examples/alarm-cases.json`）に置き、これを正本にする。

### 4.1 condition の状態

condition は次の直交した値の組で持つ。表示に使う 5 つの状態はここから導く。

| 値                   | 意味                                                                    |
| -------------------- | ----------------------------------------------------------------------- |
| active               | 発生中か（delay を満了して確定したもの）                                |
| occurrence           | 発生の回の id。発生のたびに新しい UUID v7 を振り、二度と使わない        |
| recurrence           | 回の中の再発生の数。同じ回で未確認のまま再発生するたびに 1 増える       |
| acked                | 現在の回を確認済みか（発生の前は確認済み扱い）                          |
| timer                | なし／発生待ち（on delay の満了時刻）／復帰待ち（off delay の満了時刻） |
| conditionUnavailable | condition 単位の評価不能の理由（§4.5。無ければ無し）                    |

Engine 単位の評価不能（§4.5）は condition ごとには持たず、Engine の状態として 1 つ持つ。condition が評価できるのは、Engine 単位と condition 単位のどちらの評価不能も無いときだけ。

| 表示の状態      | active | acked | 補足                                                        |
| --------------- | ------ | ----- | ----------------------------------------------------------- |
| Normal          | false  | true  | timer が発生待ちなら Pending                                |
| ActiveUnacked   | true   | false |                                                             |
| ActiveAcked     | true   | true  |                                                             |
| ReturnedUnacked | false  | false | 発生待ちでも ReturnedUnacked と出し、「再発生待ち」を添える |

### 4.2 入力と「成立」

crate が受ける入力は次の 6 種類に限る。

| 入力                  | 内容                                                                     |
| --------------------- | ------------------------------------------------------------------------ |
| 値                    | 値（数値・bool・無し）と品質（Good・Stale・Bad）、catalog での解決の有無 |
| タイマーの満了        | 単調時計の時刻                                                           |
| ACK                   | (occurrence, recurrence)、利用者名                                       |
| Engine 単位の評価不能 | 始まり（理由）・終わり                                                   |
| 定義の終了            | 定義の変更・無効化・削除・接続先の変更で condition を終える（§5.2）      |
| 復元                  | 「最後の状態」の行から始める（§5.4）                                     |

条件が成立しているかは、値と現在の active から決める（deadband で発生と復帰の境を分ける）。

- 上の限界（HH・H）: 発生中でなければ「値 ≥ 限界」で成立。発生中なら「値 ≥ 限界 − deadband」のあいだ成立のまま（「値 < 限界 − deadband」で不成立）。
- 下の限界（L・LL）: 発生中でなければ「値 ≤ 限界」で成立。発生中なら「値 ≤ 限界 + deadband」のあいだ成立のまま（「値 > 限界 + deadband」で不成立）。
- bit: 「値 = `activeWhen`」で成立（deadband は無い）。
- HH と H が同じ値でもよい（両方が同時に成立する）。
- 発生と継続の両方で等号を含めるので、deadband が 0 でも、限界と等しい値のままなら発生したまま変わらない（同じ値で発生と復帰を繰り返さない）。限界と等しい値が続く場合を fixture に入れる。

### 4.3 遷移

- 条件が成立し、発生中でない: 発生待ちを始める（on delay が 0 ならすぐ満了）。満了したら active を true、occurrence に新しい id を振り、acked を false にして「発生」のイベントを書く（`none`・`noneWithSound` は acked を true のまま。ACK のイベントは書かない）。
- ReturnedUnacked（未確認のまま復帰）から条件が成立した: 発生待ちを経て、新しい回にせず同じ回のまま ActiveUnacked に戻し、recurrence を 1 増やして「再発生」のイベントを書く。ブザー停止を解いて、また鳴らす。新しい回の id を振るのは、確認済みの状態から発生したときだけ。
- 発生待ちの間に条件が不成立になった: 待ちを捨てる。イベントは書かない。
- 条件が不成立になり、発生中: 復帰待ちを始める。満了したら active を false にして「復帰」のイベントを書く。acked はそのまま（確認済みなら Normal、未確認なら ReturnedUnacked）。`autoOnReturn` で未確認なら、続けて「自動 ACK」のイベントを書いて acked を true にし、Normal に戻す。
- 復帰待ちの間に条件がまた成立した: 待ちを捨てる。
- ACK（occurrence, recurrence）: 現在の値と同じで未確認のときだけ受け、acked を true にして「ACK」のイベントを書く。違えば「別の回」として拒否する（再発生の前の画面から送った ACK が、見ていない再発生を確認しない）。回の id は使い回さないので、作り直した condition の新しい回を古い画面からの ACK が確認することはない。評価不能の間も、待ちの間も ACK できる。
- 評価不能になった（Engine 単位か condition 単位のどちらか）: active と acked は変えず、待ちを捨てる。どちらも解けたら、新しい値でその時点から判定し直す（delay は最初から数える）。古い値や欠けた値で発生・復帰させない。
- 定義の終了: §5.2 の規則で condition を終える。

### 4.4 時刻と順序

- delay は単調時計で測る。待ちを始めたときに満了の時刻のタイマーを掛け、その時刻に判定する（1 秒ごとの tick に丸めない）。壁時計が後戻り・飛びをしても delay は壊れない。
- 順序の番号は 2 つを分ける。
  - **Engine の変更の連番**: Engine が状態を変えるたびにメモリで振る。session ごとに 1 から。`alarm_snapshot` と `alarm_changed` の突き合わせに、session id と組で使う（§5.5）。
  - **イベントの通番**: DB に書けたときに振る。履歴の並びとカーソルに使う。
- 帯・一覧の「新しい順」は、発生（または再発生）の壁時計の時刻で並べ、同じなら Engine の変更の連番で並べる。
- イベントには壁時計の時刻を付ける。Hub の source timestamp は値に付いていれば参考の列として残すが、判定や並びには使わない（無いことも後戻りもある。[SDK 設計](../../upstream/industrial/banto-tagclient-design.md)§3.2）。
- 判定に使った限界の値・deadband・読んだ値をイベントに残す。

### 4.5 評価不能と鮮度

Hub の購読は on-change 配信で、値も品質も変わらなければ何も届かない（SDK 設計§4.5）。最後に値を受けた時刻からの経過では鮮度を判定しない（変わらない正常な信号を評価不能にしてしまう）。

| 理由       | 起こるとき                                                                     | 単位      |
| ---------- | ------------------------------------------------------------------------------ | --------- |
| 未接続     | SDK の接続が Live でない（切断・再接続中・再bind中）                           | Engine    |
| 受信の途絶 | 読み直しの連続失敗が期限を超えた、または購読の張り直しが続けて失敗した（下記） | Engine    |
| 初期値待ち | 接続は Live だが、そのタグの最初の値がまだ届いていない                         | condition |
| 更新停止   | 品質 Stale（Hub の判定）                                                       | condition |
| 不良       | 品質 Bad（Hub の判定）                                                         | condition |
| 未解決     | タグの外部名が catalog に無い（削除・改名）                                    | condition |
| 値なし     | 品質は Good だが値が無い                                                       | condition |
| 型不一致   | しきい値の定義で数値でない値、bit の定義で bool でない値                       | condition |
| 非有限     | NaN・無限大                                                                    | condition |

- 明示の読み直し: Engine は一定の周期（端末の設定）で、使うタグの現在値を REST で読む。
  - 値の採否: 読み直しを送ってから応答までの間に、そのタグの購読の値が 1 つも届かず、購読の接続の世代（再接続・再bind のたびに増える）も変わっていないときだけ、読んだ値を値としても使う。それ以外は生存の確認だけに使い、値は捨てる。順序は Engine での到着順と接続の世代で決め、source timestamp には頼らない。
  - 購読の止まりの疑い: 読んだ値が受理済みの購読の値と違い、その間に購読の値が届いていなければ、購読が止まっている疑いとして読んだ値を使い、購読を張り直す（接続の世代が増える）。張り直しが続けて失敗したら「受信の途絶」にする。
  - 読み直しの失敗: 期限内に返らない・失敗するだけなら、購読が Live のあいだは評価を続け、`alarm_snapshot` に「読み直しの失敗」を警告として出す。失敗が「連続失敗の期限」（端末の設定。読み直しの周期の数倍を既定にし、値は 3-C3 で決める）を超えて続いたら「受信の途絶」にする。読み直しが一度成功すれば戻す。
- 限界（この段階で許容する制約）: いまの Hub の購読には heartbeat も配信の連番も無い。購読が無言で止まり、読み直しのときに値が前と同じ（または元に戻っている）と、止まりを見分けられず、その間に起きた変化は何度読み直しても見つからない。見逃しの時間に上限は無い。購読の生存と欠落を確かめる仕組みは上流に求める（§8）。
- Engine 単位の理由は、すべての condition を評価不能にするが、イベントは Engine 単位の 1 件（「接続の喪失」「接続の回復」など）だけを書く。接続の揺れで condition ごとのイベントが溢れ、件数の保持で本物の警報が押し出されないようにする。
- condition 単位の理由は、condition ごとに評価不能の始まりと終わりのイベントを書く。Engine 単位の評価不能の間に condition 単位の理由が変わったら、Engine 単位が解けたときの理由で始まり・終わりを書く。
- Bad を 0 や false に置き換えない。
- 認証の失効（SDK の Unauthorized。再接続しない）は評価不能ではなく、Engine の停止として扱う（§5.1）。

## 5. 製品hostの警報Engine

### 5.1 寿命と session

- `scada-host` に警報の runtime を置く。Hub の読取は、画面の表示の購読とは別に、警報の定義が使うタグだけを自分で購読する（Historian の記録元 `SdkRecorderSource` と同じく、UI の開閉に寿命を結ばない）。
- 評価は読取の更新とタイマーの満了ごとに行う（§4.4）。
- 動くのはデスクトップ版のアプリが起動し、Hub に接続し、定義を適用している間だけ。アプリを閉じれば止まる（24/365 の常駐は後続。§8）。
- session は Engine を始めてから止めるまで。次のときに session を閉じて（「Engine の停止」を書いて）、必要なら新しい session を始める: 別の Project（`projectId` が違う）の定義の適用、Hub の接続先の変更、認証の失効（理由を示し、Hub に接続し直すと再開する）、アプリの終了。同じ接続先での切断と再接続は session を閉じない（§4.5 の「未接続」）。
- session を始めるときは、アプリの起動でも、認証の失効や接続先の変更の後の再開でも、同じく §5.4 の手順で「最後の状態」から始める。
- Engine が止まっている間はブザーを鳴らさず、帯と小札に「停止中」を示す（§7）。
- 同じ PC で 2 つ目のプロセスが同じ Project の警報 DB を開こうとしたら、DB の排他 lock（Historian の記録 DB と同じ方式）で拒み、2 つ目では Engine を動かさずに理由を示す。

### 5.2 定義の適用

- 「保存した Project の定義」（§9-1）は、**ファイルへの書込みが成功した Project** とする。いまの保存は webview の書出しで、host は書込みの完了を確かめられない。そこで 3-C1 で、デスクトップ版の Project を開く・保存するを host の command（`project_open`・`project_save`。host がファイルを読み書きする）に移す。host は、いま開いているファイルの場所を知る。
- 適用は次の 2 つの経路だけで行う。どちらも host がいま開いているファイルを自分で読み、その内容の hash を取ってから定義を検査して適用する（webview が渡す Project は使わない。保存していない定義は適用できない）。
  - `project_save` の書込みが成功したとき（開発・初期設定では、保存のたびに適用する）。
  - `alarm_apply`（明示の適用）。配布やコピーで置いた Project、Editor を使わない運転端末、接続先が違って待っている状態から、適用へ進む経路。
- 権限（フェーズは [記録の host gate](historian-recording-host-gate.md)§6 の `auth-phase.json` の 4 つの値に従う）:
  - `initializing`（開発・初期設定）: ログイン不要。
  - `operational`（運用）: 保存も適用も設定変更なので、ログイン済みの Admin だけ（[アクセス方針](access-policy.md)）。保存は書込みの前に権限を確かめ、権限が無ければファイルを書かずに拒否する（ファイルと適用済みの定義が食い違ったまま再起動しないようにする）。
  - `bootstrapping`・`transitioning`・フェーズの記録が無いとき: 適用・保存の適用・ACK を拒否する（記録の入口と同じ扱い）。すでに適用済みの定義での監視は続ける。
- 適用の前の確かめ: 新しい定義で終わる未確認の回（§5.2 下記）があれば、画面は「未確認 n 件が終了します」と示して確かめてから適用する。画面は確かめた回の (condition id, occurrence, recurrence) の列を `project_save`・`alarm_apply` に添えて送り、host は適用の直前（transaction の中）に終わる未確認の回を数え直す。列と合わなければ（確かめた後に新しく発生・再発生した）適用せず、「確認し直してください」と最新の列を返す。
- 適用した定義は、警報 DB の「適用済みの定義」の表（Project ごとに 1 行。保持の上限による削除の対象にしない）に、適用した利用者・時刻・ファイルの hash・Hub の接続先の識別とともに残す。
- 適用は一つの transaction で DB に書く: 「適用済みの定義」の行、終える condition の「定義の変更」「定義の削除」のイベント、「最後の状態」の更新（終える行の削除を含む）。書けたときだけ Engine の定義を切り替える。書けなければ（DB の障害）前の定義のまま「適用できない」と返す。途中で終了しても、DB は前の定義か新しい定義のどちらかに揃っている。
- 監視中の Project: host は、最後に定義を適用した Project（`projectId` とファイルの場所）を「監視中の Project」として端末の設定に持つ。Engine が監視するのは常にこの Project で、画面でどの Project を開いているかとは別にする。別の Project を開いても（閲覧・編集）Engine は切り替わらず、画面に「この Project は監視中ではありません」と示す。監視中の Project を切り替えるのは、別の Project の定義の適用（保存による適用・`alarm_apply`）だけで、§5.2 の権限が要る（運用ではログイン済みの Admin）。
- 起動のとき: host は監視中の Project の「適用済みの定義」の表から定義を読んで、ログインなしで Engine を始める（信頼された起動の経路）。運用で未ログインのまま再起動しても、監視は止まらない（[アクセス方針](access-policy.md)の再起動の方針）。監視中の Project を開いていて、その定義が適用済みと違えば、Engine は適用済みの定義のまま動き、画面に「未適用の警報の変更があります」と示す。いまの Hub の接続先が適用したときと違えば（同じタグ名でも別の信号でありうる）、Engine を始めず「接続先が適用したときと違う」と示し、`alarm_apply` で適用し直すまで待つ。
- `alarm_snapshot` に、適用中の `projectId`・`projectRevision`・適用の時刻を入れる。

定義が変わったときの condition の扱い:

- condition ごとに、評価に関わる内容の hash を持つ。内容は、その condition の発生元の種類・タグ・`activeWhen`、その限界の値（しきい値なら自分の限界だけ）、deadband・on／off delay・`ackMode`。H だけ変えても HH の状態は引き継ぐ。
- hash が同じ condition は状態を引き継ぐ。名前・message・severity だけの変更も引き継ぐ。
- hash が変わった condition、無効にした（`enabled: false`）condition、消えた condition は、一つの規則で**終える**: 「定義の変更」（消えたものは「定義の削除」）のイベントを残し、状態と「最後の状態」の行を捨てる。ACK を別の信号へ移さない。未確認の回だったものは、イベントに「未確認のまま終了」を添える（適用の前に画面で確かめている）。hash が変わったものと有効に戻したものは、新しい condition として Normal から評価する（すでに異常なら新しい ActiveUnacked になり、ブザーも鳴る）。

### 5.3 警報 DB

- 警報イベントは、Historian の記録 DB とは別の SQLite（`%LOCALAPPDATA%\temp-scada` の下、Project の `projectId` ごとに別のファイル）に追記する。「最後の状態」「適用済みの定義」「session」の表も同じファイルに置き、別の Project の警報が混ざらないようにする。
- イベントの種類: 発生・再発生・復帰・ACK・自動 ACK・condition の評価不能の始まりと終わり・接続の喪失と回復・受信の途絶の始まりと終わり・定義の変更・定義の削除・接続先の変更・Engine の開始と停止・停止時の状態・前回の終了時の状態・状態不明の期間・記録できなかった期間。各イベントに通番、壁時計の時刻、Engine の session id と、その時点の表示の情報（定義の名前・message・severity・限界の名前）を付ける。定義を改名・削除した後も、履歴で当時の警報を識別できるようにする。ACK には利用者名を付ける（開発・初期設定では「未ログイン」）。
- 状態を変えるイベントは、「最後の状態」の更新と同じ transaction で書く。
- 保持の上限は PC の性能によるので、端末（host）の設定で「日数」か「件数」を選んで値を入れ、上限を超えた古いものから通番の順に消す。Project には持たない。既定値は 3-C で決める。1 回に消す件数に上限を置き、壁時計が先へ飛んでも一度に全部を消さない。
- 書込みの失敗（満杯など）:
  - 評価は続ける。書けなかったイベントは待ち行列にためず、件数だけ数える。`alarm_snapshot` に「履歴に書けない」とその件数を出し、一定の間隔で書込みを試す。
  - 書けない間は、ACK と定義の適用を拒否する（確認済みと返したのに再起動で未確認に戻ること、DB と Engine の定義が食い違うことを防ぐ）。
  - 書けるようになったら、一つの transaction で「記録できなかった期間」（始まりと終わりの時刻、書けなかった件数）のイベントを書き、「最後の状態」の表をメモリの今の状態で丸ごと書き直す（その間に終えた condition の行も消す）。
- DB を開けない・lock を取れないときは Engine を動かさず理由を示す。

### 5.4 session の開始と前回の終わり

- 「session」の表（1 行。保持の上限で消さない）に、直前の session の id と、正常に止めたか（「停止なし」か「停止済み」）を持つ。session には id のほかに、Project ごとに 1 ずつ増える session の世代番号を振る。session を始めるときに新しい id・世代番号と「停止なし」を書き、正常に止めたら「停止済み」にする。
- 正常に止めるときは、Normal でない condition と評価不能の condition ごとに「停止時の状態」を書いてから「Engine の停止」を書く。
- session を始めるとき（§5.1）は、次の順で行う。
  1. 「session」の行が「停止なし」なら（強制終了・電源断）、「最後の状態」の表のうち Normal でないものか評価不能のものを「前回の終了時の状態（停止の記録なし）」として書く。Engine 単位の評価不能が続いていたなら、それも 1 件書く。あわせて「状態不明の期間」（最後に書けたイベントの時刻から今回の開始まで）を書き、引き継ぐ状態はその時点のものだと一覧と履歴に示す（書込みの障害中に終わった場合も、ここで欠けが分かる）。
  2. 「最後の状態」の行ごとに、hash が適用中の定義の condition と同じで、Hub の接続先も同じなら、同じ occurrence・recurrence・acked で引き継ぐ（入力の「復元」）。待ちは捨てる。接続先が違う・hash が違う行は §5.2 の規則で終える（未確認だったものは「未確認のまま終了」を添える）。
  3. 引き継いだ行と新しい session の行を、「Engine の開始」と同じ transaction で書く（引き継いだ行は今回の session id に書き直す）。
- 引き継いだ condition は、最初の値が届くまで「初期値待ち」の評価不能として、引き継いだ状態のまま待つ。その後は §4.3 の遷移どおり: 発生中だった行は、条件が成立していれば発生中のまま（ActiveAcked はブザーを鳴らさず、ActiveUnacked は鳴らす）、成立していなければ復帰の規則で復帰する（`autoOnReturn` ならここで自動 ACK）。ReturnedUnacked だった行は、条件が成立したら再発生の規則（on delay を待ち、recurrence を 1 増やす）で発生中にする。
- 「最後の状態」の表: condition ごとに §4.1 の値（active・occurrence・recurrence・acked・conditionUnavailable）と hash・Hub の接続先・最後のイベントの通番・session id を 1 行持ち、Engine 単位の評価不能も 1 行持つ。保持の上限による削除の対象にしない。
- これにより、未確認のまま終わった警報は履歴の「前回の終了時の状態」と「停止時の状態」で判別できる。

## 6. ACK とブザー停止

- ACK は Engine の操作で、PLC の bit には書かない。
- 権限（フェーズは §5.2 と同じ）: `initializing`（開発・初期設定）ではログイン不要（利用者名は「未ログイン」）。`operational`（運用）ではログイン済みの Admin だけ。認証の DB が使えないとき、`bootstrapping`・`transitioning`・フェーズの記録が無いとき、警報 DB に書けないときは拒否する（[アクセス方針](access-policy.md)）。役割の追加は後続。
- ACK は見ている回を指す: 一覧で選んだ行の (condition id, occurrence, recurrence) を送り、表示の後に起きた新しい回や再発生は ACK しない。「すべて ACK」は、画面が持っている最新の snapshot に出ている未確認の回だけを送る。
- ブザー停止は、その端末の音を止めるだけで、ACK ではない。どのフェーズでも権限は要らない（未ログインでも止められる）。止めた状態は host が持つ（webview の再読込や複数の窓でも揃う）。新しい回が発生するか、未確認の回が再発生すると、また鳴る。
- 音は未確認（ActiveUnacked）の回があるあいだ鳴らす。`noneWithSound` の定義は、発生のときに一度だけ鳴らす。`none` は鳴らさない。鳴らすのは host（Rust）で、WebView の自動再生の制限を受けないようにする（3-E の前に実機で確かめる）。既定はアプリに同梱する短い音で、端末（host）の設定で別の音声ファイルに変えられる（既定に戻せる）。Project には持たない。ファイルが読めないときは同梱の音で鳴らし、理由を示す。

## 7. 表示

新しい primitive（画面の直下と Symbol 定義の中のどちらに置けるかは各項目に書く）:

- **警報の小札** `alarmBadge`: 定義の id と限界（しきい値なら hh／h／l／ll、bit なら無し）を指す。PLC が判定して HH などの bit を立てる案件では、小札が bit の定義を指し、文字に「HH」などを入れる。画面の直下に置く（Symbol 定義の中は §8）。
  - 検査（§3 の検査に足す）: 指す定義と限界が Project にあること。無ければ検査で拒む。
  - 色は状態ごと: Normal・発生中・未確認（発生中）・復帰・未確認・評価不能。未確認は、点滅しなくても分かるよう文字の枠（反転）で示す。発生中で評価不能が重なったら、発生中の色に「?」の印を添える（発生中を隠さない）。
  - Engine が動いていない（停止中・未適用）か、指す condition が適用中の定義に無い（保存前の新しい定義など）ときは、Normal の色ではなく「不明」の色と斜線で示す。「警報なし」と読めないようにする。
  - 点滅は §2 の UX の規則どおり既定では使わず、Project の `alarms.blinkUnacked: true` で未確認の間だけ点滅させられる。その場合も OS の「動きを減らす」設定では点滅を止め、枠の表示だけにする。
- **最新の警報の帯** `alarmBanner`: 1 件を次の優先で選ぶ。未確認（ActiveUnacked か ReturnedUnacked）を確認済みより先に、その中で severity の高い順、同じなら同じ定義の上位の限界（HH を H より、LL を L より）、それでも同じなら新しい順（§4.4）。選んだ 1 件を、復帰済みなら「復帰」と添えて「時刻・名前・メッセージ」で出し、件数を添える。画面の直下に置く。運転表示の枠のヘッダーに置く想定。Engine が動いていないときは空にせず「警報 停止中（理由）」を出す。Engine 単位の評価不能（未接続・受信の途絶）のあいだは、帯に「警報 監視できていません（理由）」を常に出し、小札も「不明」の色と斜線で示す（警報が無いように見せない）。Engine が動いていて condition 単位の評価不能があれば、帯に「評価不能 n 件（主な理由）」を常に添える（警報が出ていなくても、監視できていない信号があることを運転画面で気づけるようにする）。
- **画面切替ボタンの行き先の追加**: `navButton` の行き先に「アラーム一覧を開く」「ブザー停止」を足す（書込みを伴わない端末内の操作なので、ボタンを新設しない）。

アラーム一覧の窓（運転表示とプレビューから開く。トレンド履歴の窓と同じく、運転表示の中に描く）:

- 「現在」タブ: Normal でない condition（ActiveUnacked・ActiveAcked・ReturnedUnacked）と、評価不能の condition（状態が Normal でも）を出す。Engine 単位の評価不能（未接続・受信の途絶）のときは、先頭に Engine の理由の行を 1 行出し、Normal でない condition の行と ACK の操作はそのまま残す（Normal で評価不能なだけの condition は、Engine の行にまとめて並べない）。condition 単位の評価不能は状態とは別の列に §4.5 の理由を文字で出し、絞り込みで評価不能だけも見られる。復帰済みでも ACK するまでは残し、状態の列で「発生中」「復帰・未確認」を文字で分ける。未確認を上に、severity と新しい順（§4.4）。選んで ACK、すべて ACK（ReturnedUnacked も対象。§6）。ACK の結果が「別の回」なら、その行を最新に取り直して示す。
- 「履歴」タブ: 警報イベントの照会（期間・種類）。判定の限界と値、source timestamp を列に出す。
- Engine が動いていない（browser 版・Hub 未接続・未適用・認証の失効・DB を開けない・別のプロセスが使用中）ときと、「履歴に書けない」ときは、その理由を出す。編集中の Project と適用中の定義の revision が違うときも示す。

Designer の編集モードとプレビューは、Engine の状態を読むだけで、小札と帯にも同じ状態を出す。

## 8. 後続（この段階で作らない）

- 機器種別の slot に警報の雛形（しきい値の種類・message）を持たせ、機器インスタンスで値を入れる形。Symbol 定義の中の小札は、これと合わせて設計する。
- Shelve、latch、PLC の ACK・リセットとの連動（明示 Action）。
- 常駐（Windows サービス・トレイ）と、SCADA server core（S9b）への Engine の移設。
- 複数端末での ACK の共有、冗長化（上流 §22 で未決）。
- 警報の Replay、印刷。
- 警報の状態をタグとして Hub に返すこと（上流 §11.1 の projection）。
- 購読の生存と欠落を確かめる仕組み（heartbeat か配信の連番）を上流の Hub・SDK に求め、入ったら §4.5 の読み直しによる確認と置き換える。
- ワード割付の状態（語の値、語の中の bit）を警報の発生元にすること。当面は PLC の bit か数値のしきい値だけを発生元にする。

## 9. 確認したこと（2026-11-14 回答）

1. 評価に使う定義は、保存した Project の定義にする（推奨のまま）。デスクトップ版の開く・保存を host の command に移し、host が読んだファイルの定義を適用する。起動時は適用済みの定義をログインなしで読む（§5.2）。
2. ACK は、運用ではログイン済みの Admin だけに許す（推奨のまま）。
3. severity は 3 段（high／medium／low）にする（推奨のまま）。
4. 警報イベントの保持の上限は PC の性能によるので、日数か件数で設定できるようにする（§5）。
5. ブザーの音は、既定を同梱の音にし、変更できるようにする（§6）。
6. PLC 側で判定する場合は、PLC の bit だけを使う（§2）。
7. 案件によって自動で ACK・復帰したい警報があるので、定義ごとに ACK の種類（手動・復帰で自動 ACK・ACK 不要で鳴らさない・ACK 不要で一度鳴らす）を選べるようにする（§3）。
8. 設計を暫定の Engine の大きさに抑えるため、定義の変更で終わる未確認の回は ACK 待ちに残さず「未確認のまま終了」として終える（適用の前に画面で確かめる）。警報 DB に書けない間のイベントは待ち行列にためず、件数と「記録できなかった期間」だけを残す（2026-11-14 ユーザー選択）。
