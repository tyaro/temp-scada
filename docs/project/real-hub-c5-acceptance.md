# 実Hub記録・履歴の受入手順（C5-6）

状態: **手順（未実施）**。2026-11-10作成（日本時間）。[実Hub・S7接続計画](real-hub-connection-plan.md)のC5と、[製品hostの記録owner](../design/runtime/historian-recording-product-owner.md)§9のC5-6行を、Windows実機で受け入れるための手順と記録様式である。実施はユーザー作業とし、結果は[C0〜C3の接続記録](real-hub-c0.md)と同じく、この文書の末尾（§6）へ日時つきで追記する。

## 1. 範囲と前提

- **対象**: このWindows PCの既存Hub（`127.0.0.1:8722`）と、C3で受け入れたR系PLC（`plc_slmp.group1.*`）のタグ。記録は単一group、周期1000ms。
- **しないこと**: PLCへの書込み、Hubサービスの起動・停止・構成変更、実機側の故障注入。Bad／Staleが自然に起きなければ「未観測」と記録し、モックHubの試験（C5-2、H3b）に委ねる。HubのSIM切替でReal→SIMを起こす試験も行わない（Hubの構成変更になるため。行う場合は別途判断する）。
- **記録DB**: アプリdata dir（`%LOCALAPPDATA%\temp-scada`）の`historian\`と`historian-store.json`（§8の1）。これを検証用DBとして使う。既にある場合は、アプリを止めてから`historian\`・`historian-store.json`・`historian-store.lock`をまとめて別名へ退避し、新しいDBで始める（identity fileだけを残すと`store_identity_missing`になる）。認証DB・Hub資格情報（`scada-auth.sqlite3`・`hub-read.json`・`installation-id`）は触らない。
- **権限**: 記録の開始・停止・再開・計画適用はAdmin（認証無効モードの合成Adminを含む）。照会はViewer以上。
- **時刻**: 履歴画面の時刻入力はUTC（末尾`Z`・ミリ秒3桁）。日本時間から9時間引く。DB probe（§2.3）の時刻もUTC。

1. `work`の最新を取り、commit IDを記録する。
2. 二つのterminalで起動する（`tauri.conf.json`の`devUrl`を使う開発起動。C1〜C3と同じ経路）。

```bash

```


```bash

```

既存のwindowを残したまま別の版を試す場合は、C3と同じく`CARGO_TARGET_DIR`を別にしてビルドする。記録DBはprocessごとにwriter lockを取るので、二つのアプリを同時に起動すると後のほうは記録管理画面に`store_locked`（記録DBを開けない）を表示する。受入は一つのprocessで行う。

### 2.2 Hubの値の事前確認

```bash
cargo run --locked -p scada-host --example real_hub_read -- plc_slmp.group1.D3000 plc_slmp.group1.SCADA_C3_D4000_ZERO plc_slmp.group1.SCADA_C3_M1000 plc_slmp.group1.SCADA_C3_M1500_FALSE
```

4件が`tag_present=…:true`、`quality=good`、`source=real`で、D3000の値と行時刻が進むことを確かめる。SIM確認（§3.7）に使うタグ名を次で探し、数値か真偽値の一件を選んで記録する。

```bash
cargo run --locked -p scada-host --example real_hub_read -- --prefix s7-sim.
```

### 2.3 DB probe

記録DBの件数・欠測・Quality・DB増分は、読取専用（`mode=ro`）のprobeで見る。アプリが記録している間も実行できる。

```bash
cargo run --locked -p scada-host --example recording_db_stats
```

出力の読み方:

| 行           | 内容                                                                                                                                                                                                                      |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `file=`      | `store.sqlite3`・`-wal`・`-shm`のbyte数。DB増分は三つの合計の差で見る                                                                                                                                                     |
| `store`      | 形式・`store_id`・`deployment_id`・最終commit。`historian-store.json`の`storeId`・`deploymentId`と一致すること                                                                                                            |
| `session=`   | sessionごとの状態（`active`・`closed`・`interrupted`）、tick数、計画、開始・観測済み・終了の時刻                                                                                                                          |
| `series`     | session×系列ごとの行数（`rows`）、値のある行数（`valued`）、最初と最後の時刻の差から求めたtick数（`expected_ticks`）、数値の最小・最大、真偽値のtrue／false件数。`rows`はsessionの`ticks`、`expected_ticks`と一致するはず |
| `quality`    | session×系列ごとの`quality`・`source`・`reason`の件数。値のない行は`reason`（`bad`・`stale`・`simulationExcluded`など）を持つ                                                                                             |
| `gap`        | 記録された欠測（`samplingMissed`・`storageLoss`）と長さ                                                                                                                                                                   |
| `activation` | 開始・再開ごとの記録。適用版・mapping版・保持版とsession                                                                                                                                                                  |

### 2.4 受入用Project

[`examples/real-hub-recording.project.json`](../../examples/real-hub-recording.project.json)を使う。C3の0・false確認の画面（R系D3000・D4000、M1000・M1500、Q系D3000）に、次の記録計画（`recording:c5-6` 版1、有効、周期1000ms）を加えたもの。

| memberId               | externalName                           | 型     | C3時点の値 |
| ---------------------- | -------------------------------------- | ------ | ---------- |
| `member:r-d3000`       | `plc_slmp.group1.D3000`                | number | 変化する   |
| `member:r-d4000-zero`  | `plc_slmp.group1.SCADA_C3_D4000_ZERO`  | number | `0`        |
| `member:r-m1000`       | `plc_slmp.group1.SCADA_C3_M1000`       | bool   | `true`     |
| `member:r-m1500-false` | `plc_slmp.group1.SCADA_C3_M1500_FALSE` | bool   | `false`    |

### 3.10 実時間試験（件数とDB増分）

1. 3.9の後、記録中のまま開始時刻とDB probe（`file=`のbyte数、各系列の`rows`）を控える。
2. 少なくとも2時間、UIを開いたまま置く（最小化は可）。途中でSCADAの操作をしない。
3. 終了時刻とDB probeを控える。
4. 次を表にする。
   - 経過秒数÷周期（秒）と、各系列の`rows`の増分の差（許容: 開始・終了の境界の±2 tick）
   - `valued`と`rows`の差、`gap`の件数と合計ms
   - DB増分（3ファイルの合計の差）と、1行あたりのbyte数（増分÷増えた行数）
   - 30日保持（既定）での見込み容量（1行あたりbyte数×系列数×86400÷周期秒×30）。保持容量の検証はC6で扱うので、見込みを記録するだけとする

## 7. 既知の事象

- **K1（修正済み、2026-11-10）: workflowで無効計画を適用した後、再起動まで停止中の計画適用ができなかった**。registryのapplyの後、記録は止まるがrootは導入されたまま（slotは`Installed`）残る。修正前の`recording_reconfigure`はslotが`Installed`なら`not_allowed`で、rootを外せる`recording_resume`（無効計画では`plan_disabled`）と`recording_stop`（記録が動いていないので`not_allowed`）は画面ではどちらも無効になり、再起動まで回復しなかった。修正後の`recording_reconfigure`は、`recording_resume`と同じく、記録が動いていない静止したrootをhandoffで先に外してから適用する（記録中のrootは外さず`not_allowed`、未確定の変更を持つrootは`busy`）。
