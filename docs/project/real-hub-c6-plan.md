# 実Hub・S7接続 C6 連続運用とリリース判断の計画

作成: 2026-11-17（日本時間）。状態: **提案・未承認**。[実Hub・S7接続計画](real-hub-connection-plan.md)のC6を、試験・実装・手順書の区切りまで分けた計画である。オーナーの承認後に、実装と実機試験を別のPRで行う。この文書はアプリを変えない。

## 0. この文書の読み方

- 「実装済み」「未実装」には、根拠のファイルかPRを付ける。根拠を確かめられなかったものは「**未確認**」と書く。
- 運転の条件はユーザーが選んだ**5系列・1秒周期・24時間**とする。この条件で合格した構成と運転時間に限って「運用可能」と判断する（接続計画のC6の完了条件）。
- オーナーに決めてもらうことは§8に番号付きで並べる。本文では「確認事項n」と書いて参照する。

## 3. 容量と上限の評価

### 3.1 記録DBの見込み

C5-6 §3.10の実測（1行あたり1174.4 byte、5系列、SIMを含む）から計算する。

| 期間   | 行数（5系列×1秒） | DBの見込み |
| ------ | ----------------- | ---------- |
| 1時間  | 18,000            | 約21 MB    |
| 24時間 | 432,000           | 約507 MB   |
| 30日   | 12,960,000        | 約15.2 GB  |

- これは見込みで、24時間試験（§4.1）で実測値に置き換える。C5の実測は2時間なので、DBが大きくなったときのindexやページの増え方は含まない。
- 保持の削除を実行しない限り（§1.3）、DBは30日を超えても減らない。削除後もSQLiteのファイルは自動では縮まない（未確認。VACUUMの有無と方式は§5で決める）。
- 警報DBは、既定365日保持の見込みを未計測。24時間試験に警報を含める場合（確認事項5）に、1日の増分を測る。

### 3.2 台帳・receiverの上限との突き合わせ

| 上限                                   | 値                | 24時間で達するか           | 扱い                                                                                              |
| -------------------------------------- | ----------------- | -------------------------- | ------------------------------------------------------------------------------------------------- |
| receiver snapshot（正式＋provisional） | 64revision／8MiB  | 未確認                     | §4.1で1時間ごとに使用量を記録する。達するなら、引き上げではなく返却・退役の方式を設計する（§5.2） |
| receiver call                          | 8MiB              | 未確認                     | 同上                                                                                              |
| observation attempt                    | PR #160で回収済み | 2時間では未発生            | §4.1で再確認する                                                                                  |
| 1 rootのworkflow                       | 1件               | 計画変更を2回すると止まる  | 運転中の計画変更は1回まで。2回目は停止→再開（K2の案内）。手順書に書く                             |
| WAL物理長                              | 64MiBで保守を拒否 | C5では約4MB                | §4.1でWALの最大値を記録する                                                                       |

接続計画の方針どおり、**根拠のない上限の引き上げはしない**。上限に達した場合は、その時刻・操作・使用量を記録し、返却・退役の方式（§5.2）か運転条件の見直しで対応する。

### 3.3 ディスクの空き

- 記録DBのあるドライブの空きを、試験の前後で記録する。30日分（約15.2 GB）＋保持の削除中の一時的な増加（WAL）＋警報DBの余裕を見て、空きの下限を手順書に書く。下限の値は§4.1の実測後に決める。

## 4. 試験項目

各項目の記録は[C5受入記録](real-hub-c5-acceptance.md)§5の様式（`### C6 <番号> <日時 JST>`、操作・画面・DB probe・判定）に倣う。DB probeは`cargo run --locked -p scada-host --example recording_db_stats`（C5受入記録§2.3）を使う。時刻はUTCで書く。

共通の前提:

- 試験の前に、アプリを止めて記録DB（`historian\`・`historian-store.json`・`historian-store.lock`）を別名へ退避するか、そのまま使うかを試験ごとに決めて記録する。退避はC5受入記録§1と同じ手順。
- 「壊すもの」は試験の後に必ず戻し、戻した結果（Hubの状態、catalog revision、OSの時計、ディスク）を記録する。

### 4.1 24時間の連続記録

- 目的: 5系列・1秒・24時間で、欠測・上限・DB増分・資源の増え方が運用に耐えるかを測る。
- 手順: 新しいDBで初回設定→記録開始。画面は通常の監視状態で放置（最小化しない場合と区別して記録）。1時間ごとにDB probe、receiver・台帳の使用量（取得方法は確認事項9）、アプリのメモリ・ハンドル数（タスクマネージャーかPowerShellの`Get-Process`）、ドライブの空きを記録する。24時間後に記録を停止してjoinする。
- 測る値: 系列ごとの`rows`と期待（経過秒数）の差、`gaps`の件数と合計ms、`store.sqlite3`・`-wal`・`-shm`のbyte、WALの最大値、receiver・台帳の使用量、アプリのworking setの推移、停止・joinにかかった時間。
- 合格の基準: 期待との差が0 tick（Hub側の欠測がある場合は`gaps`として記録され、原因がHub側と特定できること）。上限による停止が無い。24時間のDB増分が§3.1の見込みの±20%以内（外れたら見込みを置き換えて§3を更新し、合否はオーナーと判断する）。メモリが単調に増え続けない（増え方の基準値は確認事項10）。停止・joinが成功する。
- 戻し方: 記録を停止する。DBは§4.8・§4.2の入力に使えるよう残す。

### 4.2 容量不足

- 目的: 実媒体で空きが無くなったときに、記録が原子的に止まり、空きを戻した後に明示再開できるかを確かめる。H2c3は一時DBのTEMP triggerで確認済みで、実ドライブでは未実施。
- 手順: 小さな別ボリューム（確認事項2）にアプリdata dirを置いて記録する。空きを埋めて`SQLITE_FULL`を起こす。画面の表示とDB probeを記録する。空きを戻し、記録を明示再開する。
- 測る値: 止まった時刻、最後に保存されたtick、画面の文言、writerの状態（`needs_reopen`）、再開後の`gaps`、DBの整合（probeが読めること）。
- 合格の基準: 途中のtickが半端に残らない。記録が止まったことが画面で分かる。空きを戻した後、明示再開で新しいsessionが始まり、止まっていた区間が欠測として残る。アプリが落ちない。
- 戻し方: 埋めたファイルを消す。別ボリュームを切り離し、data dirの置き場所を元に戻す。

### 4.3 時計の異常（前後への跳び）

- 目的: OSの時計が前後に跳んだとき、記録が止まり、誤った時刻の行を保存せず、保持の削除が誤った期限で走らないことを確かめる。
- 手順: 記録中にOSの時刻を+10分・-10分それぞれ変える（確認事項1）。NTPの同期も1回起こす。
- 測る値: 止まった時刻、最後に保存されたtick、画面の文言、時計を戻した後の再開手順と、再開後の`gaps`・clock epoch。
- 合格の基準: 跳びが1000msを超えたら記録が止まる。未来・過去の時刻の行が保存されない。再開は明示操作で、新しいclock epochで始まる。NTPの小さな補正（1000ms以下）では止まらない。
- 戻し方: OSの時刻を自動設定に戻し、同期を確認する。Hubの時刻表示も確認する。

### 4.4 Hubの停止・再起動

- 目的: Hubサービスが止まったときに、記録が欠測として残り、Hubの再起動後に自動で読取が戻るか（または明示再開が要るか）を確かめる。
- 手順: 記録中に`BantoHub`サービスを停止し、5分後に開始する（確認事項3）。`BantoHubSink`は触らない。
- 測る値: 停止から欠測の始まりまでの時間、画面の表示（Bad・Stale・切断）、再起動後に値が戻るまでの時間、`gaps`、記録sessionの状態。
- 合格の基準: 停止中の区間が欠測として記録され、値が捏造されない。Hub復帰後の挙動（自動か明示再開か）が設計どおりで、手順書に書ける。アプリが落ちない。
- 戻し方: サービスを開始し、catalog revisionと`plc_slmp`の`connected`を確認する。

### 4.5 PLC側の切断

- 目的: Hubは動いたまま、PLCとの通信が切れたときの品質・欠測の記録を確かめる。
- 手順: 方法は確認事項4。案は、Hubの管理UIで対象接続を無効化する（Hubの構成変更）か、PLCのLANケーブルを抜く。
- 測る値: Quality（Bad／Stale）が記録・表示されるまでの時間、`valued`と`rows`の差、復帰後の値。
- 合格の基準: 切断中の値がGoodとして保存されない。品質が履歴画面で区別できる。復帰後に記録が続く。
- 戻し方: 接続を元に戻し、`connected`・`source=real`を確認する。

### 4.6 アプリの強制終了と再起動

- 目的: 記録中にアプリが異常終了しても、DBが壊れず、再起動後に状態照会と明示再開ができることを確かめる。
- 手順: 記録中にタスクマネージャー（またはterminalから`Stop-Process -Force`）でアプリを止める。同じterminalから再起動する。
- 測る値: 再起動後のsessionの表示（`interrupted`など）、最後のtick、DB probeが読めること、再開後の`gaps`。
- 合格の基準: DBが開け、途中のtickが半端に残らない。中断したsessionが画面で分かる。明示再開で記録が続く。
- 戻し方: 不要（記録を停止して終える）。

### 4.7 PCの再起動

- 目的: OSの再起動（Windows Updateを含む）から、手順書だけで監視と記録を戻せるかを確かめる。
- 手順: 記録中にOSを再起動する。Hubサービスの自動起動を確認し、手順書（§6）に沿ってアプリを起動し、Projectを開き、記録を再開する。
- 測る値: 再起動から監視画面が出るまでの時間、記録の再開までの時間、欠測の区間。
- 合格の基準: 手順書の手順だけで戻せる。欠測が記録され、再開後に記録が続く。C5-7で確認した`interrupted`表示と同じ扱いになる。
- 戻し方: 不要。

### 4.8 保持（古い記録の扱い）

- 目的: 30日を超えた記録が消え、消えた区間が履歴でexpiredとして区別され、記録を長く止めないことを確かめる。
- 手順: §5.1の実装の後に行う。OSの時計を30日進めることはしない（§4.3の時計の検査と衝突するため）。案は、試験用に保持期間を短くしたDB（例: 1時間）で、§4.1と同じ構成を数時間回す（確認事項7）。
- 測る値: 削除の回数・1回の所要時間、削除中の記録の停止時間と`gaps`、削除前後のDBファイルの大きさ、履歴画面の表示。
- 合格の基準: 期限より古いtickだけが消える。期限内の行は残る。削除中の欠測が手順書に書いた範囲に収まる。DBの大きさが増え続けない（縮むかは§5の方式による）。
- 戻し方: 試験用DBを退避し、既定の30日のDBに戻す。

### 4.9 監視の再開

- 目的: 再起動の後に、監視画面へどう戻るかを確かめる。
- 手順: §4.6・§4.7の後に、Projectを開いて監視（現在値・機器小窓・履歴）が戻るまでを記録する。
- 測る値: 必要な操作の数、ログインの要否、表示が戻るまでの時間。
- 合格の基準: access-policyの要望（運用中でも再起動時はログインなしで監視画面を開ける）と、現状の差を記録する。自動起動が要るかは確認事項8で判断する。
- 戻し方: 不要。

### 4.10 運用時の認証・操作の認可

- 目的: 運用フェーズへ移行した端末で、未ログイン・Viewer・Adminの各状態で、閲覧・記録の操作・設定変更・設備操作・警報ACKが設計どおり許可・拒否されることを確かめる。
- 手順: 試験用の端末状態（認証DB・`auth-phase.json`）を退避してから、運用へ移行する。各roleでログインし、[access-policy](../design/runtime/access-policy.md)の表の各操作を試す。降格・削除・logoutで記録の購読が切れることも確かめる。
- 測る値: 操作ごとの許可・拒否と画面の文言、Rust側で拒否されたか（UIの非表示だけでないか）。
- 合格の基準: 表のとおりに許可・拒否される。未ログインで監視画面を閲覧できる。運用移行後も記録が続く（未静止のworkflowがある場合の扱いはhost gate設計§6のとおり）。
- 戻し方: 運用から初期設定へ戻す手順は未設計（§1.3）。退避した認証DB・`auth-phase.json`を戻して初期設定に戻す（ローカル編集のログイン不要を維持するため）。この戻し方でよいかは確認事項6。

## 8. 確認事項

1. **OSの時計を変えてよいか**（§4.3）。案: 記録中に手動で±10分変え、終了後に自動設定へ戻す。Hub・PLC側への影響が心配なら、HubのサービスもOSの時計を使うため、Hubの表示も合わせて記録する。
2. **容量不足をどう作るか**（§4.2）。案A: 1〜2 GBのVHDXを作ってマウントし、アプリdata dirをそこへ置く（`%LOCALAPPDATA%\temp-scada`をjunctionで向ける）。案B: 空きの少ないUSBメモリ。案Aを推す（Cドライブを埋めずに済み、試験後に切り離せる）。data dirの置き場所を設定で変える機能は無い（未確認）ので、junctionで良いかも判断してほしい。
3. **Hubサービスを停止・再起動してよいか**（§4.4）。C5では受入中のHubを止めなかった。時刻・時間帯の指定があれば教えてほしい。
4. **PLC側の切断をどう起こすか**（§4.5）。案A: Hubの管理UIで`plc_slmp`の接続を一時的に無効化。案B: PLCのLANケーブルを抜く。案C: 実施せず、モックHubの試験（C2・C5-2）に委ねる。設備の都合で決めてほしい。
5. **24時間の連続運用に警報を含めるか**（§2.1）。含める場合は、警報の定義・ブザーの音を有効にした状態で回し、警報DBの1日の増分と保持の削除も測る。含めない場合は、警報の連続運用は別の区切りとする。
6. **運用フェーズへの移行を試験してよいか、戻し方は退避ファイルの書き戻しでよいか**（§4.10）。運用から初期設定へ戻す正式な手順は未設計で、移行は元に戻せない設計（host gate設計§6）。案: 認証DB・`auth-phase.json`を退避してから移行し、試験後に書き戻す。
7. **保持の試験を、保持期間を短くした試験用DBで行ってよいか**（§4.8）。案: 1時間の保持で3〜4時間回す。製品の既定（30日）は変えない。
8. **アプリを閉じても記録を続ける必要があるか、PC起動時に監視画面を自動で開く必要があるか**（§5.2）。必要ならサービスhost・自動起動を別工程で設計する。不要なら「アプリを開いている間だけ記録する」を運用の前提として手順書に書く。
9. **receiver・台帳の使用量をどう取るか**（§4.1）。案: C6-1で、hostのlogへ1時間ごとに使用量を書く。画面には出さない。
10. **24時間で許すメモリの増え方**（§4.1）。案: 開始1時間後の値から+20%以内。
11. **配布の形**（§6）。terminalからの起動を続けるか、インストーラ（Tauriのbundle）を作るか。C6のリリース判断の対象に含めるかも決めてほしい。
12. **24時間PCを止めない日の調整**（§4.1）。Windows Updateの自動再起動を止める期間の設定（OSの設定変更になるので、オーナーが行う）と、PC・Hubに触らない時間帯を決めてほしい。
13. **合格の基準の値**（§4.1のDB増分±20%など）。この文書の案でよいか。
