## 2. temp-scada の今の形との食い違い

temp-scada は、[段階3の警報設計](../design/runtime/alarm-stage3-design.md)（2026-11-14 承認）で、警報の判定・確認・履歴・ブザーを**製品 host の中の暫定 Engine** として作り終えている（3-A〜3-E、T1〜T3）。設計は最初から「暫定」で、§8 で「SCADA server core（S9b）への Engine の移設」を後続にしていた。今回の決定で、移す先が **SCADA server core ではなく別の警報サーバー** になった。

食い違う前提は次のとおり。

## 4. 上流（#725）に確かめたいこと

凍結が明けて設計へ反映する前に、#725 の残りとして次を確かめたい。

1. **定義の持ち主**: 警報の定義（タグ・限界・deadband・遅延・ACK の種類・severity・message）は Project が持って配るのか、警報サーバーが持つのか。配るなら、配る単位と版（Project の revision か、定義だけの版か）。
2. **API の形**: 現在の状態の snapshot と変化の配信（連番・取り直しの規則）、ACK（回を指せるか）、履歴の照会（期間・種類・カーソル）。temp-scada の §5.5 の IPC の形を案として出せる。
3. **ACK の認証と記録**: 誰の操作として記録するか。SCADA の利用者を渡すのか。
4. **端末の音**: ブザーは警報サーバーの「知らせ」に入るのか、SCADA の端末の機能か。止める単位（端末ごとか全体か）。
5. **発生元の値**: 出来事の発生元の種類（警報サーバー・記録計・ほか）と、SCADA の一覧の既定の絞り込みに使う値。
6. **`scada-alarm` の扱い**: 警報サーバーの判定の芯として上流へ移すか。移すなら、§11.6 の `banto-alarm` の名前と、足りない判定（変化率・偏差・条件の組み合わせ・優先度・抑止）をどこで足すか。
7. **接続先の識別**: 警報サーバーも Hub の値で判定するので、#1295（Hub の設置の id）と #1294（Live 中の ping）は警報サーバー側の前提にもなる。
8. **長期の履歴の受け渡し**: 警報サーバーの短期のイベントを ChronoGazer の出来事の Parquet へ誰がいつ書くか。SCADA の履歴の照会はどちらを読むか。

## 5. 今の暫定 Engine をどう位置づけるか（選択肢）

| 案                              | 内容                                                                                                                                                     | 長所                                                                                                          | 短所                                                                                                                           |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 1. 暫定のまま使い続ける（推奨） | 警報サーバーができるまで、host の Engine を「暫定」として残す。新しい警報の機能（Shelve・変化率など）は足さない。表示側は API の形が決まったら付け替える | 動いているものを壊さない。O0・O4 の受入で実機・実 Hub の発報・ACK・ブザーを確かめ済み。設計が最初から「暫定」 | 警報サーバーが別の形になると、表示の受け取りの層は作り直し。C6 で測る警報 DB の数字は将来の構成と違う                          |
| 2. 警報サーバーの種にする       | `scada-alarm` と host の評価・DB を、警報サーバーの最初の実装として上流へ出す                                                                            | 作り終えた状態機械・全遷移の fixture・障害時の扱い（書けない間・強制終了後）を使い回せる                      | 上流の警報サーバーの設計がまだ無い。凍結中の範囲を超える。#1209（temp-scada を industrial へ戻す時期）と一緒に決めることになる |
| 3. 表示だけを先に切り離す       | 表示（§3.1）の入力を「警報の状態の提供元」という境界にして、host の Engine と将来の警報サーバーを差し替えられる形にしておく                              | 付け替えが小さくなる。今の e2e のモック（`mock-alarm-feed.ts`）がすでに同じ境界の近くにある                   | API の形が決まる前に境界を作ると、作り直しになりうる                                                                           |

案 1 を基本にし、#725 で API の形（§4 の 2）が見えた時点で案 3 の境界を作るのがよいと考える。案 2 は #1209 の判断を待つ。

## 6. 凍結が明けた後に書き換える文書（案）
