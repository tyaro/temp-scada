## 1. 左のタブの帯が 240px ではみ出す

### 測った結果

1600×1000 の編集モード。左の pane の既定の幅は 240px（タブの見出しの幅は 238px）。

| 表のタブ     | 帯の見える幅 / 中身の幅 | タブの幅（プロジェクト・レイヤー・部品） | 見え方                       |
| ------------ | ----------------------- | ---------------------------------------- | ---------------------------- |
| プロジェクト | 207 / 225px             | 123・57・45                              | 「部品」の右側が切れる       |
| レイヤー     | 207 / 225px             | 76・104・45                              | 両端が少しずつ切れる         |
| 部品         | 207 / 225px             | 76・57・92                               | 「プロジェクト」の頭が切れる |

どのタブが表でも、18px はみ出す。見出しの右端には、タブの帯とは別に折りたたみの ▾ が並ぶ。

### 原因（上流の作り）

- `DockedTree.svelte` のタブは `flex: 0 0 auto` で縮まず、題名は省略記号（…）にならない。帯（`.tab-strip`）は `overflow-x: auto` で横にスクロールする。
- 表のタブにだけ ⋯（`DockPanelMenu`）と ✕ が付き、そのタブだけ 47px ほど広がる（637 行目の `{#if i === node.activeIndex}`）。#378 の頃（v7.10）に書いた「タブごとの ⋯・✕」は、v9 では表のタブだけになっている。それでも、240px では収まらない。
- Banto の Issue に同じ件は無い（2026-11-26 に「タブ」「tab strip」などで検索した）。

### アプリの側でできること

1. 左の pane の既定の幅を 260px 前後にする（225px + 見出しの ▾ ほか。保存できる範囲 200〜400px の中）。設計（`frontend-ux-design.md`・`designer-ui-revision.md`）の 240px を変えることになる。
2. 題名を短くする（「プロジェクト」→「画面」など）。用語の変更になる。
3. 左の 3 つの ✕ を出さない（`close` を断る）。狭い表示の帯の ✕ を「利用者の非表示」に使っている（`designer-dock.svelte.ts` の `adopt`）ので、そのままでは使えない。

### 上流への起票（banto#986、2026-11-26 に起票）

起票時の下書き（本文は表を足して起票した）:

> **dock-svelte: 幅の狭いタブの組で、タブの帯がはみ出したことが分からない**
>
> `DockedTree.svelte` のタブは `flex: 0 0 auto` で縮まず、題名も省略記号にならない。帯は `overflow-x: auto` でスクロールする。幅 240px の 3 タブの組（題名 6・4・2 文字）では、表のタブに ⋯ と ✕ が付く分で 18px はみ出し、端のタブが切れる。スクロールバーは見えにくく、利用者は切れたタブがあることに気づきにくい。
>
> 望むこと（どれか）:
>
> - 幅が足りないときはタブを縮め、題名を省略記号にする（全文は `title`・`aria-label`）。
> - または、はみ出したことを示し、表のタブを見える位置へスクロールする（今は表のタブへスクロールしている）。
> - または、表のタブの ⋯・✕ を見出しの右（▾ の隣）へ出す選択肢。
>
> 再現: `ThreePaneDock` の左に 3 つの pane のタブの組を置き、幅 240px にする。

### Banto v9.1.1 での確かめ（2026-11-26）

banto#986 は v9.1.1 で直った（タブが縮み、題名が省略記号になる）。同じ条件（1600×1000、編集モード、左 240px）で測り直した（使い捨ての spec、コミットしていない）。

- 標準の密度ではみ出しは無くなった。ただし表のタブは ⋯・✕ に幅を取られ、題名が「レ…」のように 1 文字まで縮む。ほかのタブも「プロジェ…」「部…」になる。全文は `title`・`aria-label` に残る。
- touch の密度は上流の注意のとおり最小幅に達して横スクロールに戻る（51px はみ出す）。SCADA は今 touch の密度を使っていない。将来 touch の密度を使うなら、上流のタブには `touch-action: none` が付いていて、題名を指で横に払っても帯はスクロールしない。幅 240px の 3 タブで、指だけで端のタブを選び ⋯・✕ を操作できる経路を確かめる（locator の自動スクロールでは確かめられない）。

## 2. 狭い表示へ切り替えると、開いているタグの選択の窓も隠れる

### 確かめた動き

Inspector の「タグを選択」から窓を開き（1600×1000）、そのまま 900×800 にした。

- 窓は消える。DOM には残っていて、祖先の右の引き出し（`.flyout.edge-right`）が `hidden`・`inert` になっている。
- 帯の Inspector を開き直すと、窓はまた見える（#378 の記録のとおり）。
- **見えないまま Esc を押すと、窓が閉じる**（#378 の記録に無かった動き）。Banto の `OverlayPanel` は Esc を window で受けるので、見えなくても閉じる。

### 原因

- `TagPicker`（Banto の `Modal`）は `InspectorPanel.svelte` の中に置いてある（1975 行目）。`Modal` は `position: fixed` の `div` を置いた場所にそのまま描く（body へ移したり、最前面の層（top layer）に出したりしない）。
- 狭い表示では、dock は Inspector を端の帯へ移し、引き出しが出ていない pane の中身を同じ DOM のまま `hidden`・`inert` にする（`DockAutoHide.svelte` 21〜22 行目・257〜258 行目。App は全 pane を `persistent` にしている）。窓もいっしょに隠れる。

### 見えない間の影響（コードから。画面では確かめていない）

- App の `isTagPickerOpen()` は true のままなので、Designer のキー操作（F キー・Ctrl 系のコマンド）が止まる（`designer-shortcuts.svelte.ts` の `functionKeysReady` 78 行目、`routeBeforeCommands` 255 行目）。利用者には理由が見えない。
- 設備の台帳（`EquipmentLibrary.svelte` 549 行目）の `TagPicker` も同じ形。こちらは作業タブの中なので、dock の帯とは関係しない。

### 直し方の候補

1. 窓を開いているあいだに狭い表示へ切り替わったら、`revealInspector()` で Inspector の引き出しを開く（窓が見えたままになる）。小さい変更で済む。
2. `TagPicker` を pane の外（App の直下）に置く。窓は画面全体のものなので、置き場として素直。ただし、Inspector の入力欄への受け渡し（`pickerRequest`・`chooseTag`）を外へ出す必要がある。
3. 切り替わったら窓を閉じる。選びかけた候補が消える。

1 が小さく、2 が筋がよい。

直したときに確かめること（#397 のレビューより）: 幅を狭い・広いと往復させたときと、見えないまま Esc で閉じた後に、隠れた窓が出てこないこと。Designer のキー操作が戻ること。

## 3. Inspector を開く依頼の承認待ちに左の一括の表示を始めると、引き出しがどれも開かない

### 再現（遅延モックの単体試験。手元だけ）

`designer-dock.svelte.test.ts` の `setup(true)` と同じ遅延モックで、次の順にした。

1. 左をまとめて隠す（承認を通す）。
2. Inspector を帯から外した状態で、`revealInspector()` を呼ぶ（`right:true` が承認待ちになる）。
3. 承認を待つ間に `setSidebar(true)` を呼ぶ。
4. 承認をすべて通す。

結果: 依頼は `right:true`・`left:true`・`layers:true`・`parts:true` の順に通る。最後に開いている引き出しは無い（`flyout` が `null`）。Inspector の引き出しが開いているのが望ましい。

### 原因

- `revealInspector()` は引き出しの意図（`flyoutIntent`）を Inspector にしてから、承認を待つ。
- 待つ間に `pushLeft` が `intend(id)` を呼び、意図を「pane 無し」（一括の処理が自分で決める）に上書きする。
- 一括の処理は終わったときに自分が意図の持ち主なので、`settleFront` → `closeLeftFlyout()`（左の引き出しだけを閉じる）を行う。
- `revealInspector()` は待った後に `flyoutIntent === intent` でなくなっているので、引き出しを開かない。

逆の順（一括の表示の承認待ちに Inspector を開く）は #378 で直してあり、単体試験「keeps a later Inspector drawer open after an old reveal-all (narrow)」で守っている。

### 直し方の候補と落とし穴

- 手元で「`intend(id)` が pane 無しのときは、Inspector の引き出しの意図を上書きしない」と試した。再現の試験も既存の 64 件も通った。
- ただし、この形では Inspector の意図が開き終えた後も残る。利用者が帯のタブで左の引き出しへ切り替えた後でも（`noteFlyout` は切り替えを「閉じた」と数えない）、後の一括の表示が終わるときに Inspector を開き直してしまう。
- 守るのは、`revealInspector()` が承認を待っているあいだだけにする。たとえば、承認待ちの Inspector の意図を別に持ち、`revealInspector()` の終わりで外す。一括の処理は、承認待ちの Inspector の意図があれば上書きしない。
- `intend(id)` を通るのは左の一括の表示だけではない。狭い表示へ切り替えたとき左の pane を帯へ並べる処理（`designer-dock.svelte.ts` の狭い表示の effect）も通るので、同じように扱う（#397 のレビューより）。
- 守るのは、自動の処理・一括の処理に対する承認待ちの意図だけにする。承認待ちのあいだに利用者が左のタブを明示に選んだ（`showLeftPane`）ときは、その新しい選択を優先する。
- 試験: 上の再現の順、「開き終えた後に左へ切り替え → 一括の表示 → Inspector を開き直さない」、「承認待ちに左のタブを明示に選ぶ → 選んだタブが勝つ」の 3 本。狭い表示への切り替えの経路も 1 本。
